# 索引儲存與候選方案實測比較（2026-09-19）

本次以使用者指定的 `/Users/hermes/Downloads/測試用資料` 唯讀測試。來源資料約 5.4 GiB、471 份一般檔案；LocalDocSearch 內容解析器處理其中 151 份，成功保存的文字為 9,596,713 bytes、約 11.5 萬個區塊。其餘檔案只有 metadata，因此不能用 5.4 GiB 原始檔大小直接推算全文索引比例。

原始量測資料見 [storage-backend-comparison.json](storage-backend-comparison.json)，重跑程式為 `scripts/compare-storage-backends.mjs`。

## 比較方式

- 以 0.20.0 現有索引結果作唯一正確性基準。
- 12 組查詢包含一字中文、二字中文、三字以上中文、英文縮寫、較長片語、無結果及 `--all-terms`。
- 每種方案暖機一次、量測五次，並比較完整命中文件集合，不只比較前 20 筆。
- 候選索引只允許多抓；最後仍解壓原文並用 NFKC、小寫、連續子字串規則核對。12 組查詢的四個原型都與現況完全相同，沒有漏回或誤回文件。
- 原型搜尋目前只計算完整命中集合，尚未產生產品片段與最終排序；因此不能把原型時間直接當成正式 CLI 延遲承諾。

## 結果

| 方案 | 資料庫大小 | 相對現況 | 搜尋峰值 RSS | 最慢查詢 p95 | 判斷 |
|---|---:|---:|---:|---:|---|
| 現況 `candidates()` 全載入 | 17.70 MiB | 100% | 477.6 MiB | 247.8 ms | 空間與 RAM 基準 |
| 現況資料表改為逐列串流 | 17.70 MiB | 100% | **104.7 MiB** | 154.8 ms | 最低風險的 RAM 修正 |
| 每文件 Brotli q5 | **3.80 MiB** | 21.5% | 263.4 MiB | 118.5 ms | 最小，但大文件需整份解壓 |
| 64 KiB 分塊 Brotli q5 | 4.46 MiB | 25.2% | 213.9 MiB | 119.3 ms | 儲存基礎候選 |
| 分塊 Brotli＋FTS5 trigram | 12.16 MiB | 68.7% | 180.2 MiB | 117.6 ms | 候選快但空間成本高 |
| 分塊 Brotli＋Bloom trigram | 6.02 MiB | 34.0% | 183.3 MiB | 116.5 ms | 候選效果接近 FTS，明顯較小 |

RSS 是同一個搜尋 worker 連續跑完 12 組查詢的程序峰值。現況產品路徑同時建立完整候選陣列、區塊陣列、正規化文字、排序與片段；原型只保留命中集合，因此最有把握的結論是「現況整庫載入確實是主要 RAM 問題」，不是各數字可以直接當正式版保證。

首次用現況產品解析來源約 5.3 秒，程序峰值約 734 MiB。表中的 Brotli／FTS／Bloom 建置時間是從已解析的現有 SQLite 轉換，沒有重跑 Office／PDF 解析，不能和 5.3 秒直接比較；額外轉換約為 Brotli 0.46～0.49 秒、FTS／Bloom 1.58～1.67 秒。Bloom 原型建置峰值約 320 MiB，仍需改成分段建立，不能原樣用於大資料集。

## 候選索引的實際差異

三字以上查詢時，FTS5 常把 471 份縮到實際命中數，例如「使用者」18 份候選／18 份命中、較長片語 1／1、無結果 0／0。Bloom 對應為 20／18、1／1、0／0；少量誤判由原文核對移除，不影響精確度。

一字與二字沒有 trigram，兩種候選索引都必須掃描 471 份。包含二字詞的 `--all-terms` 也可能退回全掃描。這表示 FTS 或 Bloom 不能取代可控記憶體的串流核對路徑。

## 本輪結論

1. **先修搜尋讀取方式**：現有未壓縮 SQLite 改逐文件／逐區塊串流，就把本次峰值從 477.6 MiB 降到 104.7 MiB，且完全不改索引格式。這應作為下一版第一步，也能成為後續壓縮方案的安全核對器。
2. **正文採 64 KiB 左右獨立 Brotli 塊**：本批索引從 17.70 MiB 降至 4.46 MiB，保留隨機讀取與大型文件的記憶體上限。每文件單塊雖再少 0.66 MiB，但不值得承擔大文件整份解壓。
3. **暫不採 FTS5 trigram**：它比單純壓縮多 7.70 MiB，而三字以上候選效果沒有明顯優於 Bloom。
4. **Bloom 作第二階段候選原型**：總量 6.02 MiB，只有 FTS 方案約一半；仍需把建置改成分段、驗證修改／刪除及更多料號與標點查詢。正式採用前也要評估文件數增加時逐一讀 Bloom 的成本。

建議的實作順序是：M18 先讓現有 SQLite 搜尋串流化並保持所有結果／排序／片段一致；M19 再遷移到版本化 Brotli 分塊；最後才決定是否加入 Bloom。每一步都能單獨回滾，也能用現有引擎做結果差集。

## 限制

- 這批 5.4 GiB 大部分是目前不解析的媒體或其他格式；真正影響索引的是約 9.6 MB 擷取文字。
- 151 份可解析文件不足以代表數萬份文件；尤其 Bloom 掃描數量與 SQLite 查詢成本仍需合成放大測試。
- Brotli q5 是可攜的 Node 內建方案；尚未與 zstd 在相同資料、相同分塊與相同正確性條件下比較。
- 本次在 macOS、Node.js 26.7.0 執行，沒有 Windows 實機數據。
